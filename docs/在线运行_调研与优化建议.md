# 在线运行（浏览器内 Turtle）调研与优化建议

> 调研对象：`app/utils/turtle-interpreter.js` + `app/components/TurtleRunner.vue`
> 方法：用 Chromium 真实渲染全部 113 题页面 Canvas，与 `public/images/posts/turtle100/*.png` 参考图逐一对比；并实测开源方案 Skulpt 的 turtle 渲染效果。

## 一、现状诊断（结论先行）

113 题全部「能跑、不报错、有输出」，但**视觉还原度差**，问题分两类：

### 1) 几何错误：`circle()` 实现是错的（影响最大）
- 113 题中 **34 题用 `circle`**，其中 **20 题用负半径**（`circle(-s)`），这类基本画错。
- 例：第 73 题本应是**一圈圈同心圆**（半径 20,30,40,50,60），线上实际画成**并排的韦恩图**（圆整体横向漂移）。第 59 题四个圆位置也错位。
- 根因：`circle()` 用「沿当前朝向前进弦长 + 转向」近似，与真实 turtle「圆心在左侧 90°、沿弧运动」不一致，导致圆心漂移；半径符号/大半径时误差放大。
- 正例：正方形/三角形/梯形/斜线等**不含 circle** 的题，几何基本正确。

### 2) 呈现（UI）问题：所有题都存在
- **过度放大/裁切**：Canvas 自动贴合包围盒，图形撑满画布、没有参考图那种留白边距。
- **线太粗**（`lineWidth` 随缩放放大，最多 ×1.6），显得粗糙；参考图是细线。
- **缺少 turtle 光标**（小箭头）：参考图有，我们没有。
- **缺少坐标标注/角度标注/说明文字**：参考图有 `0 / 100 / 140`、`90°`、题面文字（如「最小圆的半径是 20」），我们只有一个蓝色原点圆点。
- 结果：即便几何对的题（如三角形），也只能「看出是个三角形」，观感与参考图差距明显。

## 二、开源方案调研

| 方案 | 是否含 Python 解释器 | 体积(gzip) | 依赖/离线 | 适配 113 题 | 结论 |
|---|---|---|---|---|---|
| **Skulpt** (`skulpt/skulpt`, MIT) | 是（Python 2/3 子集，JS 实现）| **~234 KB**（skulpt.min 140K + stdlib 94K）| 纯前端，可离线自托管 | **实测 5 类题全部 ok，turtle 几何正确**（含负半径 circle、同心圆）| 最成熟的现成方案 |
| **bjpop/js-turtle** | 否（只有 turtle 绘图 API，不含 Python 解析）| ~几 KB | 纯前端 | 需自己写 Python→JS 或转译，仍要保留解释器 | 只能替换「绘图层」，不能替解释器 |
| **Brython** turtle | 是（完整 Python 3 转译）| ~数 MB | 纯前端 | 可用但重，启动慢 | 太重 |
| **basthon-turtle / PyWebLib (Pyodide)** | 是（真 CPython/WASM）| ~10 MB 级 | 需一次性下载 WASM | 真 turtle，最逼真 | 与「秒开/零依赖」目标冲突，SEO 页不合适 |
| **自研（现状）** | 是 | **~10 KB** | 零依赖 | 语法全过；circle 有 bug + 呈现差 | 最轻，修一修可达标 |

### 关键实测：Skulpt 的 turtle 是否更准？
把第 66/73/59/60 题喂给 Skulpt，**画出的图形与参考图高度一致**（尤其 73 同心圆、59 四圆位置完全对）。说明「正统 turtle 语义」能还原这些题——问题出在我们自研版 `circle` 的近似算法。

### Skulpt 的代价
- 体积 **约为自研的 23 倍**（234KB vs 10KB gzip）。对 113 个 SEO 落地页，意味着更长的首屏下载与更大的带宽；虽然可 tree-shake / 懒加载（运行模块进入视口再加载），但「秒开」会打折扣。
- 引入一个 60 万行级 JS 运行时做后台维护，后续升级、调试、定制（我们要在画布上画坐标标注、说明文字）反而受制于它的渲染层。

## 三、建议（分层结论）

**不建议整体替换为 Skulpt。** 理由：真实差距只有「circle 算法 + 呈现细节」两处，而自研版体积小 23 倍、零依赖、完全可控。重写/替换成 234KB 的运行时，收益（几何正确）与代价（体积、可控性、SEO 首屏）不成正比。

推荐 **在自研版上做两项修复**（工作量小、见效快、保持零依赖秒开）：

1. **修 `circle()`（必修，影响 34 题）**
   - 改为标准 turtle 语义：圆心 `(x + r·cos(h+90°), y + r·sin(h+90°))`（负半径在右侧），沿弧按角度采样 `lineTo`，结束位置/朝向与 CPython 一致。
   - 保留 `extent`（圆弧/半圆）与 `steps` 参数。
   - 用 113 题 + Skulpt 结果做回归对比验证。

2. **改呈现（影响观感，全部题）**
   - 固定世界坐标系与缩放：以原点为中心、固定宽高（如 400×320 世界单位映射），保留边距，不自动贴合裁切。
   - 线宽用固定值（如 1.5）不随缩放放大；画 turtle 小三角光标；可选画 0/100 等刻度与说明文字。
   - 保留现有「运行 / 重置 / 复制」交互与 SEO 文案。

修完后可用同一套「渲染 113 题 → 与参考图对比」的脚本做回归（已在 `/tmp/render.mjs` 思路中验证可行）。

## 四、一句话回答用户
「市面上最成熟的浏览器 turtle 是 Skulpt，实测能正确还原这些题，但它有 ~234KB、是自研的 23 倍，和『零依赖秒开离线』目标冲突。而你现在的效果差，**90% 是一个可修的 `circle()` 算法 bug（34 题受影响）+ 画布呈现（过度放大、线太粗、没有 turtle 光标和坐标标注）**。建议直接修自研版，不换库。」

## 五、第二轮优化（动画过程 + 抖动修复）

参考 CPython 3.15 的 `Lib/turtle.py` 继续优化，解决两个问题：

### 1) 「点运行直接出图，没有运动过程」→ 改为逐笔动画
- 旧实现：解释器一次性画出全部 → 画布直接出现完整图形。
- 新实现：解释器先记录一串**有序绘制动作**（line / dot / text / fill / moveCursor），再由前端用
  `requestAnimationFrame` 回放：
  - 按**累计行进距离**（世界坐标）推进，而不是一次性揭示整段。长 `fd()` 会让海龟**平滑滑过去**，
    圆弧则沿弧线**扫出**，海龟小箭头始终停在当前笔尖位置。
  - 用离屏 canvas 累积「墨迹」，每帧再合成「墨迹 + 海龟光标」，避免光标拖影。
- 计时贴合 turtle 的 `speed()`：默认 speed=3；速度越大动画越快，`speed(0)`/`fastest` 为瞬出；
  动画时长按屏幕上的行进像素定速（约 380px/s 起），并做 0.9–7s 的上下限，短图也看得清。

### 2) 「画布抖动」→ 固定变换 + 不重设尺寸
- 抖动根因：旧 `renderCanvas()` 每帧都 `canvas.width/height = ...`（会清空画布并触发布局回流），
  且每帧用「当前已画部分」重新算包围盒 → 缩放反复变化。
- 修复：整幅图的**世界变换只算一次**（基于完整动作集），动画全程复用；
  画布 backing store **只在 CSS 尺寸真的变化时**才重设。实测多页面动画全程 canvas 尺寸仅初始化时变 1 次，不再抖动。

### 3) 几何进一步对齐 CPython
- `circle()` 的自动分段数改为 CPython 公式 `steps = 1 + int(min(11 + |r|/6, 59) * frac)`，
  圆的折线密度与官方一致（更接近参考图）。
- `rt/lt/seth/home/circle/goto/teleport` 均在上报光标位姿，动画中朝向正确。
- 首屏进入时先渲染「空白网格+原点」，再自动运行动画，避免一进页面就是完整图。

### 回归验证
- 113 题全部渲染通过；与参考图像素差 **mean 4.66→4.88、max 9.34**（几何未退化，动画相关差异来自绘制中截帧）。
- 类型检查：TurtleRunner.vue 已无类型错误（剩 2 条为 `[...slug].vue` 历史遗留，与本次无关）。
- `npm test` 6/6 通过；多页面动画期间 canvas 无重复 resize（不抖动）。

## 六、第三轮修正（初始朝向）

- 问题：所有图形一开始方向朝上（海龟初始 heading=90）。
- 依据 CPython `turtle.py`：`START_ORIENTATION["standard"] = Vec2D(1.0, 0.0)`，即初始朝**东/右**，heading=0。
- 修复：解释器 `state.heading` 初值与 `reset()`、前端 `cursor`/`poseAfter` 的初始朝向全部由 90° 改为 **0°（向右）**。
- 验证：第 1 题 `fd(100)` 现为水平向右直线（与参考图一致）；第 4/9/18 题方向与参考图一致；113 题渲染通过，参考图差异 mean 4.87→4.75、max 9.46→8.67。
- 补修：`home()` 也应把朝向复位为 0°（向右），依据 CPython `home(): goto(0,0); setheading(0)`。此前误留 `turnTo(90)`，导致第 12 题等以 `home()` 结尾的图形方向不对；已改为 `turnTo(0)`。

## 七、全面命令测试（测试驱动发现并修复的 bug）

新增两套测试：`tests/turtle-interpreter.test.mjs`（58 个用例，逐条验证命令语义）+ `tests/turtle-questions.test.mjs`（113 题回归，确保都能跑且出图）。`npm test` 共 66 项全过。

测试过程中发现并修复了三个**真实 bug**（此前静默出错，用户感知为“画错了”）：
1. **长名称别名全是空操作**：`forward/back/backward/right/left` 在底层 `api` 对象上根本不存在，`t.forward(100)`／`t.right(90)` 调用后**什么都不做**（只是经命名空间转发到 undefined）。已补齐为 `fd/bk/rt/lt` 的别名。这是最严重的一个——学生用常见长名写的图会完全错误。
2. **`pensize()` 无参读取返回 NaN**：`pensize(w)` 只处理了设置，改成无参时返回当前笔宽（getter）。
3. **不支持 `from turtle import *` / `from turtle import fd, rt`**：解析器只处理 `import`。已新增 `parseFromImport`，星号导入把所有命令绑定为裸名字，命名导入绑定指定名字。

测试覆盖：运动(fd/forward/bk/back/backward)、转向(rt/right/lt/left/seth/setheading/heading/home)、goto 家族(goto/setpos/setposition/setx/sety/teleport)、画笔(pu/penup/up/pd/pendown/down/isdown)、查询(pos/position/xcor/ycor/distance/towards)、circle(整圆/负半径/半圆/extent/steps/0)、颜色与笔宽(pensize/width/pencolor/fillcolor/color 含命名/rgb/hex)、填充(begin_fill/end_fill/filling/fill/__finish 自动闭合)、dot/write、可见性(ht/hideturtle/st/showturtle/isvisible/__finish 姿态上报)、speed(数值/名称/越界归 0)、no-op 命令、clear/reset、pen()；语法(for/while/def 带参与 return/if-elif-else/四则与 //%/ ** 优先级/比较/and or not/一元负/增强赋值/列表与索引/range/len/abs/min/max/int/float/round/注释/分号多语句/关键字参数/from-import)。

## 八、动画匀速化（对齐 CPython turtle.py 的 hop 模型）

反馈：不同指令动画速度不一致（有的快有的慢/有的几乎瞬移）。

依据 CPython 3.15 `turtle.py` 的真实模型（关键源码）：
- 移动 `_go`/`_goto`（speed=s>0，tracing=1）：
  `nhops = 1 + int(画布像素距离 / (3 * 1.1**s * s))`，每 hop 画一小步，每步之间 `_delay(_delayvalue)` 固定毫秒。
  → **每帧前进的屏幕像素 = 3·1.1^s·s（对给定 speed 是常数）**。
- 旋转 `_rotate`：`anglevel = 3.0 * s`，`steps = 1 + int(|角度| / anglevel)`，每步之间同样固定 `_delay`。
  → **每帧转动的角度 = 3·s（常数）**。
- 即：**每一帧耗时相同**，线段越长帧数越多、转角越大帧数越多——整体就是“恒定速度”。这正好是期望的“所有指令速度一致”。

旧实现的问题：我原来按“总路径长度/总时长”推进，**转向是零长度 move → 不占时间**，`dot/text/fill` 用固定权重，导致转向类指令“瞬移”、速度不一致。

新实现（重写动画核心）：
- 把每个操作展开成“帧（hop）”序列：`line` 按 `3·1.1^s·s` 像素/帧切；`move` 的转动按 `3·s` 度/帧切（位移也按像素 hop）；`dot/text/fill` 视为瞬时 1 帧。
- **所有帧用同一个 frameMs**（按 speed 决定 6~16ms），总时长过长时**等比例缩短每帧**（保持相对均匀），不改变“各指令同速”。
- 修正了 `segHeading` 的 360° 环绕导致的多余整圈帧（归一化到与累计 heading 最接近的等价角）。
- 验证（帧数与 CPython 公式一致）：
  - fd(100)=7 帧、fd(200)=13 帧（随距离线性）；
  - rt(90)=11 帧、rt(180)=21 帧（随角度线性）；
  - 正方形 4×(fd100+rt90)=72 帧 = 4×(7+11) 精确；
  - 每帧等时 → 屏幕上匀速。
